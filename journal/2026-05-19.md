## Post-deployment Fix 1.1 — the lastSyncedStatus lie

First post-Fix-1 user repro at 03:10 UTC showed `executeGroupCreate SUCCESS` fired (mappings populated, parent closed via `closeCommanderParentIfAllLocalTasksDone`) BUT no `CATCH_UP` log line, no `cmd task update <child-id>` in the writer log, and an orphaned child appeared in housekeep doctor output.

Root cause traced through the data:

- `extensions/tasks.ts:953` (the toggle path) calls `addPendingCreate(syncState, task, ...)`. When the pending entry already exists (which it does after `new-list`), `addPendingCreate` UPDATES the entry's `desiredStatus` to the new `task.status`.
- So by lambda resolve time, `pendingCreates[0].desiredStatus = "done"` (the latest toggle's status).
- `applyGroupCreateResult` then wrote `lastSyncedStatus: pending.desiredStatus = "done"` on the new mapping.
- BUT cmd's `task add` always creates with `status: "pending"` (local "idle"). The mapping was LYING — claiming we synced "done" when only "pending" was actually persisted.
- Fix 1's drift filter saw `current="done" === lastSyncedStatus="done"` → no drift → no catch-up update → child orphaned.

Fix 1.1 (committed in this slice): `applyGroupCreateResult` always sets `lastSyncedStatus: "idle"` regardless of pending's desiredStatus. The mapping now reflects what cmd actually persisted, not what the user momentarily wanted. Drift detection now correctly fires the catch-up.

**Existing test that pinned the buggy behavior** at `commander-sync.test.ts:517-533` ("records desired pending status when tasks changed before group mapping resolved") was REWRITTEN to assert the correct behavior with an explicit comment explaining why the old behavior was wrong. **Regression test** added in `commander-sync-status-catchup.test.ts` exercising the exact user-toggled-during-inflight path that broke the live repro.

Final stats: **1966 passing / 16 unrelated baseline failing / 0 blast-radius regressions.**

This is the SECOND time a "test pinning implementation shape rather than behavior" obscured a real bug (the first was Phase 0's `tasks-parent-complete.test.ts` source-text-grep tests). The lesson reinforces: behavior > shape for assertions, every time.

### Lessons

- **Parent ↔ children isn't a thing you build once.** Pi creates the parent at `group:create` time and then largely forgets it until the auto-close at mission-complete. The gap was where mid-progress comments, brief edits, label sync, and reopen-on-undo all live. Each gap was small individually; together they were the difference between a board that lies and a board that tells the truth.
- **Soft warnings are cheaper than hard blocks.** False-positive cost of the validation-card heuristic is one extra line of output. Hard-blocking would have refused legitimate edge cases (e.g., "Test framework refactor"). The label + nudge is enough — agents who care will heed; agents who don't will at least leave an audit trail.
- **Audit before you legislate.** When Ricardo asked "did we create too many tasks?", the natural reflex was to add a hard-block on >N children. Reading the actual offending cards first revealed they were *dummy validation* — different shape from real over-creation, fixable by a label convention, not a count limit. The audit kept the fix proportional.
